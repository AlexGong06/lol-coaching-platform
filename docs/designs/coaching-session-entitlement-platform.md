## Problem Statement

Alex coaches League of Legends players. Today students reach out over Discord DMs,
agree on a time by hand, and pay through an informal channel. There is no booking
surface, no payment gate, and no automatic control over who can enter the Discord
coaching space or when.

A platform is being built to replace that manual flow. It has a second purpose: it
is a project Alex is submitting to **Corgi** (corgi.insure) around a software
engineer screening on **2026-11-16**. As of 2026-11-13 Alex has decided it will
**not** be the primary thing discussed in that screening, which removes the hard
deadline from the design without removing the audience. Corgi is a full-stack
insurance carrier; its renters-insurance platform Beagle automates enrollment,
billing, compliance, claims, and physical fulfillment. Corgi's job description asks
for state machines with real financial consequences, messy third-party data
ingestion, real money flows, integration-heavy systems with monitoring, and
end-to-end ownership of production systems.

So the deliverable has to satisfy two readers at once: a student who wants to book
and attend a session, and an engineering team deciding whether to hire. The second
reader is no longer on a clock, which means the project can be finished properly
rather than to a date.

## Demand Evidence

- Alex has coached students before this platform existed. Verbatim: *"I've coached
  people before without this platform so the product should absolutely be usable by
  a potential student."* This is behavioral, not hypothetical — the coaching already
  happens and already gets paid for.
- The current workflow is Discord DMs plus manual payment, which means the pain
  points are observed rather than imagined: no-shows, "did my payment go through,"
  timezone confusion, and manually letting people into the server.
- The evaluating audience is named and specific: Corgi's CTO and engineering team,
  with a known job description and a known date.

What is *not* established: volume. Nothing in this session established how many
students per week, so the design assumes low concurrency and does not invest in
scale. Correctness under concurrency is still enforced at the database level
because it is cheap there, not because volume demands it.

## Status Quo

Students message Alex on Discord, the two of them settle on a time by hand, and
money moves informally. Discord server access is granted manually and never
revoked. Nothing records what was agreed, nothing confirms payment against a
session, and nothing ends access when a session ends.

Every feature in the recommended approach maps to a specific failure of this
workflow. That mapping is the README's opening paragraph, and it is the most
credible framing the project has: this replaces something real, and the thing it
replaces can be described precisely.

## Target User & Narrowest Wedge

**Two users, one system.**

1. **The student** — a League player who wants a one-hour session, picks a slot,
   pays, and gets into the coaching voice channel at the right time without
   messaging anyone.
2. **The evaluator** — a Corgi engineer who reads the repository, may click a live
   link, and is deciding whether Alex can own a production system where mistakes
   cost money.

**Narrowest wedge:** a student can go from landing page to *inside the voice
channel at the right time* without Alex touching anything. That single path — book,
sign in with Discord, pay, receive a working join link at window open and nothing
before it — is the whole product. Everything else is optional.

**What the wedge no longer claims.** Access ending is not automatic. The join link
dies at window close, so nobody new gets in, but a student already in the server
stays there until Alex removes them. See *Access model* for why that is acceptable
here and exactly what it costs.

## Constraints

- **No hard deadline.** This was the most architecture-shaping constraint in the
  original plan — 45-55 working hours against the 2026-11-16 screening — and as of
  2026-11-13 it is gone. Four of the seven planned days had already elapsed when Alex
  decided the project would not lead the screening, and rather than compress a
  56-hour plan into three days the work is now ordered by dependency (see *Build
  order*). The remaining estimate is **44.5 hours**, which is the sum of the eleven
  phases and is stated as information rather than as a budget. No *scope* decision in
  this design rests on the clock any more; where sequencing still does — external lead
  time in Phase 0, deploy before features in Phase 2 — the reason is dependency and is
  stated as such. Anything that was justified only by the deadline has been removed.
- **Stack is partly prescribed** by the evaluator: Go, TypeScript, React/Next.js,
  PostgreSQL, AWS (S3, SQS, ECS), Docker.
- **Alex is basically new to Go.** This is the constraint that shaped the
  architecture more than any other.
- **Dual delivery:** the repository must stand alone for a reader who never runs
  it, *and* a live link must work.
- **One rehearsal before any real student.** The feature freeze is gone with the
  deadline, but the thing the freeze existed to protect is not: the whole path must be
  exercised once, end to end, by a real second person on their own device and their
  own Discord account, before live mode is enabled. That is a gate on *shipping*, not
  on a date.
- **A dedicated Discord server, not Alex's community server.** This became a hard
  requirement with the invite-only access model, for the reason given in *Access
  model*: once a student is in the server, `@everyone` is all that protects every
  other channel in it.

### Verified platform constraints

These were confirmed by research during the session and are load-bearing:

| Constraint | Consequence |
|---|---|
| Riot Sign On (RSO) OAuth requires an **already-approved production** API key; dev keys do not qualify, and review runs weeks to months | "Log in with Riot ID" is **not buildable** on any near-term timeline |
| Riot `by-riot-id` → PUUID lookup **works on a development key**; RSO only governs `/accounts/me` | Match-data ingestion is viable without RSO |
| Riot **development keys expire every 24 hours** | Ingestion must degrade gracefully and stay off the money path |
| Discord invite `max_age` is a **countdown from creation**, capped at 604800s (7 days). There is no settable expiry timestamp; the `expires_at` in the response is derived from `created_at + max_age` and is read-only | An invite **cannot be minted in advance to become valid later**. It must be created *at* window open, which is why a scheduled worker survives the simplification |
| A Discord invite gates **joining the guild, not remaining in it** | Invite expiry removes nobody. This is the whole reason access-ending is manual in this design |
| Removing a role does **not** disconnect a member already in a voice channel; "Disconnect Members when Roles Removed" is still an open Discord feature request | Confirmed by research 2026-11-13. No longer load-bearing here, but it is why the superseded role design needed a separate force-disconnect call |
| Invite `temporary: true` ("grant temporary membership") removes the member when they disconnect from voice, unless a role was assigned. Community-documented, not in the official reference | **Deliberately unused.** A dropped connection mid-session would eject a paying student whose single-use invite is already spent |
| `DELETE /invites/{code}` needs **Manage Channels** on the channel (or Manage Guild); `GET /channels/{id}/invites` the same | Two of the bot's three permissions |
| Reading guild membership (`GET /guilds/{g}/members/{u}`) would require the **`GUILD_MEMBERS` privileged intent** | **Deliberately not used.** The bot reads and writes invites on one channel and nothing else; it cannot see who is in the server. *(Alex, 2026-11-13: all member operations happen in the Discord app; the code does link generation and expiration.)* |
| AWS SQS `DelaySeconds` caps at **15 minutes** | SQS cannot schedule anything for a session days out; the Postgres due-work table does the scheduling |
| Discord member verification / rules screening leaves a joining member `pending` | A `pending` member cannot connect to voice, which looks exactly like the access system failing. **Decided: screening stays off** on the coaching server, since the invite is already single-use and window-bound, and a Phase 0 checklist item verifies it |
| Stripe Checkout `expires_at` has a **30-minute minimum**, measured from session creation | The slot hold is 30 minutes and is created in the same transaction as the Checkout session |

## Premises

1. **Dual audience.** Corgi's engineers may read it; real students will use it once
   live mode is enabled. "Usable by a student" means the student-facing path is
   complete and exercised end to end by a real second person on a test card **before
   live mode is switched on** — a gate on shipping, no longer on a screening date.
   The live-money switch is a deliberate config change (see Payment mode).
   *(Corrected by Alex during the session — the original premise treated it as a
   demo only.)*
2. **Riot ID login is out; Discord OAuth replaces it.** Discord OAuth identifies the
   student and yields the email address the access notification needs. It no longer
   yields a `guilds.join` token, because the student now joins by clicking a link.
   Riot ID becomes a profile field used for match lookup, not authentication.
3. **The paid, time-windowed access lifecycle is the centerpiece.** Premium before
   coverage attaches, an effective window, and a credential that provably stops working
   when the window ends. Depth here
   beats breadth anywhere else. **Amended 2026-11-13:** revocation now means the
   credential is destroyed and a removal obligation is recorded, not that the platform
   ejects the member. That is a weaker guarantee and a more honest one, and it is
   still the same lifecycle.
4. **TypeScript owns the money path; Go owns ingestion.** A Go component is
   **mandatory for the submission**: it was exempt from every cut rank when a cut
   list existed, and it survives the list's removal unchanged. *(Revised during the
   session — see Cross-Model Perspective.)*
5. **Both deliverables required:** a standalone README plus architecture docs, and
   a working deploy.
6. **Two-way calendar sync and a designed marketing page are the lowest-signal
   items.** Cut to an `.ics` download and a clean modest page, roughly 1.5 hours
   total. With the deadline gone there is no gate on the styling half; it simply
   lands after the functional page.
7. **No code in this system moves money backwards.** Refunds are a manual act by Alex in
   the Stripe dashboard, reserved for platform failure; everything else is non-refundable
   and says so at checkout. Inbound refund and dispute webhooks are recorded and change
   no state. This is a scope decision with a correctness dividend: the defects a refund
   path produces cannot occur in a system that has none.
8. **Access ending is a tracked manual obligation, not an automated action.**
   *(Alex, 2026-11-13: "I'm ok with having to manually remove users since in my own
   workflow, once a student is done, I'm likely going to remove them from the server
   anyways.")* The platform's job is to make that obligation visible, dated and
   auditable.

## Approaches Considered

### Approach A: Entitlement engine, depth-first (minimal viable)
Next.js + TypeScript with a separate worker entrypoint in the same image. Discord
OAuth, DB-enforced booking holds, Stripe Checkout with idempotent webhooks,
Postgres due-work reconciler, `/ops` page, S3 presigned VOD upload. Docker +
compose committed, deployed on a PaaS. Risk Low, Completeness 7/10. AWS surface
limited to S3, and **no Go at all**.

### Approach B: AWS-forward on ECS (ideal architecture)
Identical application code on ECS Fargate behind an ALB, reconciler as a second
service, ECR + CI. Completeness 9/10. **Rejected:** ECS + IAM + ALB + ECR for a
first-timer is the likeliest single cause of shipping a dead link, and a partial ECS
setup reads worse than a documented deferral. The deadline's removal does not revive
this: the reason was never only the hours.

### Approach C: A, plus Go ingestion in the core (selected)
Approach A built in A's order, with a minimum Go ingestion service promoted **into
the non-negotiable core** so that Go cannot vanish from the submission. The
charge-file reconciler that was originally a second add-on is **out of the plan** —
not for want of hours, which are no longer scarce, but because it belongs after a
working loop. Recorded as the first post-launch extension.

## Recommended Approach

**Approach C.** Every item below is committed. The cut list that used to rank them
was a deadline instrument and is gone; what remains is the *Build order*, which says
when each piece is built rather than which gets dropped. Two items were never
cuttable at any point and still are not: the payment-to-entitlement path and the Go
ingestion service.

### Identity and payment

- **Next.js (App Router) + TypeScript**; PostgreSQL with migrations; a second
  entrypoint in the same image runs the worker. Docker + `docker-compose.yml`
  committed so the whole system runs locally with one command.
- **Discord OAuth** (`identify`, **`email`**) is the only login. `guilds.join` is
  **no longer requested**: the student joins by clicking an invite, so the app never
  acts on their behalf against Discord, and the entire stored-token and
  refresh-rotation protocol the original design needed is gone with it. The `email`
  scope is still required and not optional — `identify` alone does not return an
  email address, and six committed behaviors depend on having one: the confirmation
  email with `.ics`, the pre-session reminder, **the access email at window open**,
  the expired-hold-race notification, the Alex-cancellation notice, and the
  platform-failure notice that accompanies an `expired_unfulfilled` refund. Capturing it
  at login rather than from Stripe means it is available *before* payment, which the
  expired-hold notification needs.
- **The booking form captures the Riot ID.** *(Alex, 2026-11-13: "I will ask for the
  riot ID on registration for a slot.")* One required field on the booking form, stored
  as `bookings.riot_id` in `gameName#TAG` form, validated for shape only — never against
  the Riot API at booking time, because a dev key that expires every 24 hours must not be
  able to block a payment. A malformed or unknown ID therefore costs nothing: the Go
  ingestion simply finds no matches for it, and Alex asks in the session. This is the
  input the mandatory Go deliverable reads.
- **The no-refund policy is disclosed before payment, not after.** Shown beside the price
  on the booking page, enforced as a tick in Stripe Checkout via
  `consent_collection` + `custom_text.terms_of_service_acceptance` so acceptance is
  recorded on the Stripe session and retrievable as dispute evidence, and restated in the
  confirmation email. See *Cancellation* for the wording and the single
  platform-failure exception.
- **Payment mode (decided):** the deployment runs **Stripe test mode** until the
  rehearsal has passed. **That is the only gate on live money anywhere in this
  document** — no date, no screening, no other condition. That rehearsal is performed by
  a real second person
  on their own device and their own Discord account using a Stripe **test card**, so the
  unattended path is genuinely exercised without moving real money through an app no
  outside person has ever used. Live cutover **once the rehearsal passes** is a config
  change: swap keys, create live Price objects, re-verify the webhook signing secret, run
  one real transaction, then enable public booking. The README states this plainly.
- **Three SKUs** as Stripe Price objects created in Phase 4, USD, amounts fixed:

  | SKU | Price | Duration | Effective rate |

  | VOD Review | **$30** | 1 h | $30/h |
  | Live Coaching | **$40** | 1 h | $40/h |
  | Both | **$60** | 2 h | $30/h |

  Stripe amounts are integer cents: `3000`, `4000`, `6000`. Note for Alex rather

### SKU semantics

All three SKUs are **scheduled, synchronous sessions**. They differ only in duration
and in whether a replay upload is expected beforehand. Everything else — slot,
window, Discord access, cancellation policy, fulfillment — is identical.

| SKU | Duration | Consumes a slot? | Window | Discord access | `.rofl` upload | Fulfilled when |
|---|---|---|---|---|---|---|
| **Live Coaching** | 1 h | Yes | = the booking | Invite at window open | No | Window closes |
| **VOD Review** | 1 h | Yes | = the booking | Invite at window open | Expected | Window closes |
| **Both** | 2 h, contiguous | Yes | = the booking | Invite at window open | Expected | Window closes |

**The upload is not a precondition.** If the replay has not arrived by session start,
the session runs anyway and part of it is spent helping the student locate and upload the
file — Alex's stated intent, and the reason this design has no missing-upload fallback
branch and no deadline check. A reminder at T-24 h asks for the file in advance so the
full hour goes to the review, but nothing is gated on it.

Consequently there is **one policy for all three SKUs** (see Cancellation), one
fulfillment rule (the window closed), and no review state machine.

### Replay upload

**Committed, not cuttable.** *(Alex, 2026-11-13: "the clients will only have to upload.")*
Two of three SKUs promise it, the T-24 h reminder asks for it, and it is the only honest
reason S3 appears in the project. The previous draft called it both committed and "first
to go", which is a cut rank in all but name; it has no cut rank.

**Upload only. Retrieval is out of scope and out of the application.** Students `PUT` a
file; **Alex fetches it from S3 by hand** — console, CLI or a synced folder — and plays
it locally in the League client. The app has **no download route, no signed GET, no
listing UI and no playback**, which removes the whole read side of the feature and is why
it costs about an hour.

**How presigned PUTs actually work**, because the previous draft described something S3
does not do:

| Claim in the previous draft | Reality |
|---|---|
| "The `upload_grant` row authorizes PUTs from payment until session end plus one hour" | **S3 never consults our database.** A presigned URL is authorized by its signature and its own expiry alone. Once issued it works until that expiry regardless of any row. |
| A grant spanning payment to session end | A SigV4 presigned URL has a **7-day maximum lifetime**, so a URL minted at payment for a session three weeks out cannot cover the window at all. |
| "accepts League replay files and nothing else" | A plain presigned PUT **accepts any bytes of any size**. Extension and size are not checked unless the signature pins them. |

**So the mechanics are:**

- The `upload_grant` row gates **issuing a URL**, not the PUT. `POST /bookings/:id/upload-url`
  checks the caller owns the booking and the grant is `open`, then mints a URL valid for
  **15 minutes**. Short-lived and minted on demand, so the 7-day ceiling is never
  approached and a closed grant stops new URLs even though it cannot revoke one already
  issued. The README states that a URL already in a student's hands stays usable for up to
  15 minutes after the grant closes, which is the honest residual.
- The signature **pins `Content-Type: application/octet-stream` and a
  `content-length-range` of 1 MB to 100 MB**, so the 10-40 MB envelope is enforced by S3
  rather than advised. The `.rofl` extension is enforced in the key name the app chooses;
  a determined student could still upload non-replay bytes under a `.rofl` key, and the
  README says so rather than claiming a validation that does not exist.
- The bucket blocks public access, has **no public read**, and a lifecycle rule
  **expires objects after 30 days** — Alex has fetched the file by then, and old replays
  are unplayable on newer patches anyway.
- **Every cancellation path closes the grant** in the same transaction that writes the
  terminal state, exactly as `member_cleanup` is written. The previous draft left a
  fully-refunded cancelled student with upload rights until their original session time.

Known limitation for the README: a `.rofl` only opens in a League client on a matching
patch, so a sufficiently old replay may be unplayable. A domain constraint, not a system
failure.

### Booking, holds, and overlap

- Availability is stored as **continuous open ranges** (a recurring rule in Alex's
  timezone), **edited by direct SQL or a seed row for this release** — no admin UI
  (Open Question 4). Continuous ranges rather than pre-cut one-hour slots, because
  the Both SKU is a contiguous 2-hour booking and cannot be assembled from fixed
  1-hour cells.
- **One-off unavailability is a table, not a UI.** *(Alex, 2026-11-13: "lets include a
  blackout table.")* `blackouts (starts_at timestamptz, ends_at timestamptz, note text)`,
  rows inserted by direct SQL for this release. Availability search subtracts them, and
  **the exclusion constraint covers them too**: a blackout writes a `reserved` range the
  same way a booking does, so the database refuses a booking that overlaps one even if
  the search is wrong. Without this the first time Alex is ill or travelling the picker
  keeps selling those hours, a student pays for a session Alex cannot attend, and the
  time-based rule marks it `completed` with no money owed — the one case where this
  design's simplicity would quietly produce an unfair outcome. Open Question 4 defers the
  admin screen, which is reasonable; it never deferred the table, because direct SQL
  needs somewhere to write.
- **SKU selection comes before the calendar.** The picker cannot search availability
  until it knows whether it needs a 1-hour or a 2-hour contiguous opening, so the
  flow is: choose SKU → choose time → pay.
- **Empty-day messaging for the Both SKU (decided).** When a day holds open time but
  no contiguous 2-hour block, the day renders **empty with an explicit per-day note:
  "No continuous 2-hour blocks on this day."** Per-day, not a global banner, so the
  student can see at a glance which days are worth checking. Without it a fragmented
  calendar is indistinguishable from a broken one — and this is the only place in the
  product where "no availability" has a cause the student would otherwise have to
  guess at.
- A **15-minute gap** is reserved after every booking, enforced by the database (see
  below), so two windows can never be open at once and a departing student cannot
  overlap the next session even with the revoke lagging a full poll interval.
- **Availability search applies the same padding as the constraint, on both sides.**
  A start time is offered only if `[start, end + 15 min)` overlaps no existing
  `pending_payment`/`paid`/`active` booking's reserved range. Without this the
  picker would cheerfully offer 3:05 after a 2:00-3:00 booking and the insert would
  then be refused by the database. The Both SKU's "continuous 2-hour block" test
  includes the trailing gap, so the committed empty-day note is accurate rather than
  optimistic.
- **A constraint rejection is not a concurrency loss, and says so.** "That slot was
  just taken" is reserved for a genuine race. A rejection the search should have
  prevented shows "That time is no longer available — the calendar has been
  refreshed", reloads availability, and is logged as a search/constraint
  disagreement, because recurring instances mean the search is wrong.
- **Minimum lead time: 45 minutes, enforced twice.** The picker offers only future
  occurrences and nothing starting sooner than 45 minutes from now — and the floor is
  **re-checked inside the transaction that creates the hold and the Checkout
  session**, measured from that moment, not from when the page was rendered. Search
  alone is not enough: a picker left open for twenty minutes would otherwise walk a
  stale slot straight past the floor. A stale start reuses the "That time is no
  longer available — the calendar has been refreshed" path. Measuring the floor from
  Checkout-session creation is what keeps it strictly longer than the session's own
  30-minute life. This is
  load-bearing, not politeness: the Checkout session lives 30 minutes, so a slot
  starting in 5 minutes could be paid for after its own window had already opened —
  leaving a student who paid for a session that is partly or wholly in the past, and
  a session that is partly or wholly in the past. Bookings cannot be made inside the
  window, so `expired_unfulfilled` always means a platform failure and the manual refund
  it flags stays correct.
- **A lapsed hold is swept by the poller.** The exclusion constraint keys on
  `state`, not on a timestamp, so an abandoned Checkout would block its slot *and*
  its gap forever until something writes the terminal state. At hold creation a
  due-work row is enqueued for the hold's expiry instant; the same ~30-second poller
  claims it with `FOR UPDATE SKIP LOCKED` and transitions the booking to
  `expired_hold`. The slot is not re-offered until that transition lands.
- **The hold is created when the Stripe Checkout session is created, not at slot
  selection.** Stripe measures its 30-minute minimum `expires_at` from *session
  creation*; a hold started earlier at slot selection would always need an
  `expires_at` less than 30 minutes away and Stripe would reject it. So: picking a
  slot in the UI reserves nothing, clicking through to pay creates the hold and the
  Checkout session in one transaction, and the hold is set to expire **60 seconds
  after** the Checkout session. Stripe therefore refuses payment before the slot is
  released, which closes the *authorization* race — a new payment cannot start once
  the slot is free. It does **not** close webhook-delivery lag: a payment completed
  at minute 29 can deliver after minute 31, which is exactly the deliberate remainder
  the Expired-hold race handler below exists to absorb. Two students on
  the picker at once is resolved first-click-wins, and the loser is told the slot
  was just taken.
- Overlap and double-booking are prevented **in the database**, by a Postgres
  exclusion constraint:

  ```sql
  -- A stored, trigger-maintained range. NOT a generated column and NOT an
  -- inline expression: see the note below.
  ALTER TABLE bookings ADD COLUMN reserved tstzrange;

  CREATE FUNCTION bookings_set_reserved() RETURNS trigger AS $$
  BEGIN
    NEW.reserved := CASE WHEN NEW.starts_at IS NULL THEN NULL
      ELSE tstzrange(NEW.starts_at, NEW.ends_at + interval '15 minutes') END;
    RETURN NEW;
  END $$ LANGUAGE plpgsql;

  CREATE TRIGGER bookings_reserved BEFORE INSERT OR UPDATE ON bookings
    FOR EACH ROW EXECUTE FUNCTION bookings_set_reserved();

  ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
    EXCLUDE USING gist (reserved WITH &&)
    WHERE (reserved IS NOT NULL
           AND state IN ('pending_payment','paid','active'));
  ```

  **Why a trigger and not the obvious inline expression.** The natural form,
  `EXCLUDE USING gist (tstzrange(starts_at, ends_at + interval '15 minutes') WITH &&)`,
  **does not compile.** An `EXCLUDE` constraint builds an index, PostgreSQL requires
  index expressions to be `IMMUTABLE`, and `timestamptz + interval` is only `STABLE`
  — adding `'1 day'` and `'24 hours'` to a timestamptz give different answers across
  a DST boundary, so the operator's volatility is per-function, not per-argument. The
  migration would fail with *"functions in index expression must be marked
  IMMUTABLE."* Wrapping the arithmetic in a hand-declared `IMMUTABLE` function would
  work and is a known trick — safe here only because a fixed 15-minute interval has
  no day or month component — but lying to the planner about volatility can silently
  corrupt an index, and it is a bad thing to have to defend in an interview. The
  trigger keeps the derivation in the database, where a buggy application write
  cannot bypass it, and indexes a plain stored column.

  **The gap lives inside the reserved range, so the database enforces it.** Book
  2:00-3:00 and Postgres reserves 2:00-3:15; nothing can start before 3:15. The gap
  — not the overlap check — is what keeps a departing student out of the next session
  while revoke lags up to a poll interval, and that guarantee should not depend on
  slot-generation code being correct. One constraint covers duplicate bookings,
  overlapping windows, variable durations, and the gap.

  `reserved IS NOT NULL` is defensive rather than load-bearing now that every SKU is
  a scheduled session: `tstzrange(NULL, NULL)` is *not* null but the unbounded range
  `(,)`, which overlaps everything, so a future windowless product would otherwise
  block the whole table.
- **Timezones:** every window stored as a UTC instant; availability stored as a rule in
  Alex's timezone. **The student's IANA zone is captured at booking** from
  `Intl.DateTimeFormat().resolvedOptions().timeZone`, posted with the booking and stored
  on the row, because emails render outside a browser and have no viewer to ask. The
  picker renders in the live browser zone, every email renders in the stored zone, and
  both zones are shown on the confirmation so a mismatch is visible rather than silent.
  A missing or unrecognized zone falls back to UTC with the offset spelled out.

### Booking and entitlement states

One enumerated set, referenced by the exclusion constraint predicate, the
cancellation table, the reconciler's notion of an open window, and the README
diagram.

**Booking states**, each transition with its writer named, because an unwritten
transition is the defect this table exists to prevent:

| From → to | Written by |
|---|---|
| — → `pending_payment` | the booking service, in the transaction that creates the hold and the Checkout session |
| `pending_payment` → `paid` | the Stripe webhook handler, in the transaction that creates the entitlement |
| `pending_payment` → `expired_hold` | the due-work poller at the hold's expiry instant |
| `expired_hold` → `paid` | the webhook handler's expired-hold race, when it re-checks and the slot is still free |
| `expired_hold` → `payment_orphaned` | the same handler, when the slot was taken |
| `paid` → `active` | the window-start due-work row, in the same transaction that moves the entitlement to `open` |
| `active` → `completed` | the window-end due-work row, when at least one code reached `issued` |
| `active` → `completed_unfulfilled` | the same row, when no code ever reached `issued` |
| `paid` → `completed_unfulfilled` | the same row, when the poller missed window start entirely and the entitlement never left `pending` |
| `pending_payment` or `paid` → `cancelled` | the cancel path (student control or `/ops`), before window start |

**Terminal:** `completed`, `completed_unfulfilled`, `cancelled`, `payment_orphaned`.
**`expired_hold` is not terminal** — the expired-hold race moves out of it in both
directions.

**Money moving backwards never changes a booking state.** This is a structural rule,
not a convention. Refunds and disputes are appended to **`money_events`**
(`refund_recorded`, `dispute_opened`, `dispute_closed`, each with the Stripe event id,
amount and arrival time) and the booking's own state is left exactly as it was. A
dispute on a session delivered three weeks ago therefore cannot overwrite `completed`,
cannot re-open a closed entitlement, and cannot release a slot. The previous design
moved money and state together and produced precisely those three bugs.

**Entitlement states:** `pending` (created, window not yet open) → `open` (window
current, one code should be live) → `closed` (window ended with at least one code
issued). Terminal branches: `voided` (cancelled before the window opened),
`expired_unfulfilled` (the window ended and **no code was ever issued** — the only
platform-failure path). Written by:

| From → to | Written by |
|---|---|
| — → `pending` | the webhook handler, with the booking's `paid` transition |
| `pending` → `open` | the window-start due-work row |
| `open` → `closed` | the window-end due-work row, when at least one code reached `issued` |
| `open` → `expired_unfulfilled` | the same row, when no code ever reached `issued` |
| `pending` → `expired_unfulfilled` | the same row, when window start was missed entirely |
| `pending` → `voided` | the cancel path |

There is no `revoked` state. Nothing in this design can cut access short: refunds are
not issued by code, the operator refund control is gone, and the bot cannot remove a
member. Deleting an invite mid-window would stop new joins only, which Alex can do by
hand in Discord if it ever matters. A state with no writer is a lie, so it is gone.

**The window-end rule is keyed on code issuance, never on the clock.** This resolves an
ambiguity the previous draft left open with money attached. Whenever the window-end row
runs — on time, or late after a crash or a deploy — it asks one question: did any
`access_invites` row for this entitlement ever reach `issued`?

| At window end | Booking | Entitlement | Money |
|---|---|---|---|
| At least one code reached `issued` | `completed` | `closed` | None. Session delivered. |
| No code ever reached `issued` | `completed_unfulfilled` | `expired_unfulfilled` | **Alex owes a manual refund.** Red in `/ops`. No code moves money. |

A late pass therefore cannot refund a session that was delivered, and cannot silently
absorb one that was not. The clock decides *when* the row runs; the code record decides
*what it writes*.

**There is no no-show branch.** A student who never clicks and a student who attends the
whole hour both resolve to `completed` with no money movement, because the platform sold
a window and delivered a window. *(Alex, 2026-11-13: "a completed session will always
logically resolve to the same state in the backend.")* This also disposes of the
returning-student case: a student already in the guild needs no invite, clicks nothing,
and is fulfilled identically.

**Removal-obligation states** (one row per terminal entitlement, in `member_cleanup`):
`queued` → `done`, ticked by Alex in `/ops`.

A row is written by the pass that writes the terminal entitlement state, in the same
transaction, for every entitlement reaching `closed` or `expired_unfulfilled`. Not for
`voided`: no window ever opened, so no code existed and nobody could have joined.

**Stated limitation, not a gap to be closed later.** `done` is an operator
self-report and **nothing verifies it**. The system cannot see who is in the server, by
design, so this table records that an obligation existed and that Alex said it was
discharged — nothing more. Verification would require a membership read the bot
deliberately does not have, so the limitation is published rather than engineered
around. It is in the README's failure-modes table in these words.

**Which definition of "open" is authoritative:** the **stored state** governs the
reconciler's diff; the **due-work rows** govern the transitions that set it. A window
that has started but whose row has not yet run issues nothing, which is correct and is
the only direction that matters: access never opens early. The opposite direction is
handled by the window-end rule above, which is keyed on the code record rather than the
clock precisely so that a late pass is still correct.

### Payment-to-entitlement

- **Stripe Checkout (hosted)**, `expires_at` = creation + 30 minutes, with the hold
  expiring 60 seconds later, so no card data ever touches the app.
- The webhook handler is the **only** writer that creates an entitlement:
  signature-verified, idempotent on `event.id` via a `processed_events` table,
  inside one transaction with the booking state transition.
- **Expired-hold race:** if a webhook arrives for a booking whose hold lapsed, the
  handler re-checks the slot. Still free → reseat and proceed. Taken → booking
  `payment_orphaned`, student emailed, **row raised red in `/ops` for Alex to refund by
  hand**. This is a system fault, so the no-refund policy does not apply: the student
  paid and has no session. No code issues the refund, here or anywhere.
- **Checkout return page:** shows "confirming payment" and polls booking state. If
  the entitlement does not exist after 60 seconds it tells the student the
  confirmation email is authoritative and stops spinning.

### Access model: one single-use invite per booking

**The primitive.** When the window-start row runs, the worker creates **exactly one**
invite on the coaching voice channel:

```
POST /channels/{channel_id}/invites
{ "max_age": <ends_at - now(), in whole seconds>,
  "max_uses": 1,
  "unique": true,
  "temporary": false }
```

The code is stored against the entitlement in `access_invites`, under a plain
`UNIQUE (entitlement_id)` constraint. At window close, or when the entitlement reaches
any terminal state, the worker calls `DELETE /invites/{code}`; a 404 counts as success.

**One code per booking, for the life of the booking.** *(Alex, 2026-11-13: "Limit one
code per customer. If a stranger uses it, then it's the client's problem and we will not
issue a new one.")* The worker never mints a second code for the same entitlement, and
this single sentence is what makes the rest of the model honest:

- **`max_uses: 1` now genuinely caps a leaked link at one join.** The previous draft
  reissued whenever a code vanished from Discord, and since Discord deletes a single-use
  invite *the instant it is used*, every use triggered a replacement. A link posted
  publicly would have admitted a fresh stranger every poll interval — roughly 120 over
  an hour — while the student simply refreshed the booking page for the current code.
  With no reissue, a leaked link admits one person and is then spent.
- **A vanished code is never diagnosed and never replaced.** A used code, a
  hand-deleted code and an expired code are indistinguishable to this bot. All three mean
  the same thing operationally: there is no live code, and there will not be another.
- **The cost, stated plainly.** If the worker crashes between creating the invite at
  Discord and committing the code, that booking has a live code the database does not
  know about and will never issue another. The student cannot reach it. That window ends
  `completed_unfulfilled` and Alex refunds by hand — the platform-failure path, working
  as intended, for a genuine platform failure. Alternatively Alex posts an invite from
  the Discord app and the session proceeds; the booking stays flagged either way.

**`max_age` is the exact remaining window, with no floor and no clamp.** Computed as
`ends_at - now()` at the moment of the call. **If that is not strictly positive the
worker creates nothing** and the window-end rule resolves the booking instead — Discord
reads `max_age: 0` as *never expires*, so an unguarded computation on a poller running
late would mint a **permanent** credential after the session ended. There is no
round-up: a code minted with 10 seconds left is valid for 10 seconds. The previous
draft's 60-second clamp existed to avoid racing a reissue, and with no reissue there is
no race — so the invariant every issued code dies at or before `ends_at` holds without
exception, which is what the crash-safety argument in mandatory test 7 depends on.

**Why this still needs a scheduler.** `max_age` counts down from *creation*, so an invite
cannot be minted in advance to become valid at 2 PM. It has to be created at 2 PM.

**How the student gets the link.** Two surfaces, in priority order:

1. **The booking page**, authenticated by their Discord login, where the confirmation
   email and the `.ics` both point. It polls and reveals the join button the moment the
   code exists, with a countdown before that. Primary surface because it has no delivery
   latency inside a window measured in minutes.
2. **An access email at window open**, best-effort. If it lands late the booking page has
   already worked.

**The button is an app route, not a raw Discord URL.** `GET /bookings/:id/join` checks the
caller owns the booking and the entitlement is in state `open` — the stored state, not
the clock, matching the rest of the design — stamps `consumed_at` on the code's row, and
302s to `https://discord.gg/{code}`. The stamp records *intent*, not arrival, which is
all it can honestly claim.

**`consumed_at` is telemetry and nothing commercial reads it.** It exists so `/ops` and
the README can say how often students actually use the link, and so a support question
has an answer. The route writes it because the route is already there; if it were load
bearing it would be a problem, because Discord gives this bot no way to observe a join.

**The student who is already in the server.** Clicking an invite to a guild you are
already in neither joins you nor consumes the invite. **Nothing detects this and nothing
needs to.** The code is issued as normal, sits unused, and is deleted at window close.
The booking page reads **"Join the session"** either way, with one line below it:
*"Already in the server? The voice channel opens at your start time."* Fulfillment is
time-based, so the unused code costs nothing and changes no state. In practice the case
is uncommon, because Alex removes the student as the session ends.

**What this guarantees, stated precisely:**

- **Nobody can join before the window opens — for anyone not already in the server.** No
  code exists to join with, and the positive-`max_age` guard means none can be minted
  outside the window either. This was Alex's stated core requirement. The qualifier is
  not a weasel: a guild member already inside needs no invite, which is why removal at
  session end is part of the operating model, and why that removal is an operator
  guarantee rather than a platform one.
- **Nobody new can join after the window closes.** The code is deleted, it was
  single-use, and its own `max_age` had already expired it.
- **A leaked link admits one person.** Genuinely, now that nothing reissues.
- **A student already inside the server is not removed.** Not at window close, not ever,
  until Alex removes them by hand.

**The exposure, named rather than buried.** Without a bot-managed role there is no
per-student channel permission, so the coaching voice channel must be open to
`@everyone` in the server and **the server itself is the access boundary**:

1. **This requires a dedicated coaching server.** On Alex's community server every
   paying student would acquire permanent `@everyone` access to every channel in it.
2. **A student not yet removed can enter a later session.** Bounded rather than
   eliminated: the exclusion constraint and the 15-minute gap guarantee windows never
   overlap, so this needs a stale member *and* Alex not noticing someone in a voice
   channel Alex is sitting in.
3. **A stale member holds more than the voice channel.** Until removed they hold
   `@everyone` on every channel in the coaching server: message history, the member
   list, and therefore the client list. That is the real blast radius, and it is why the
   server must contain nothing but the coaching channels.
4. **The guarantee is one-sided by construction.** The platform can prevent access from
   starting; it cannot end access. Every statement of it carries that asymmetry.

This is a real downgrade from the superseded role design, and the README says so in those
words. It is accepted because it matches what Alex already does — *"once a student is
done, I'm likely going to remove them from the server anyways"* — and because a tracked
manual step is more honest than an automated one nobody has tested.

**The named upgrade path**, for when the core loop is done: a **per-member channel
permission overwrite**, `PUT /channels/{channel_id}/permissions/{user_id}` with
`type: 1`, allowing `VIEW_CHANNEL` + `CONNECT` for one member while `@everyone` is
denied. It needs Manage Permissions on the channel, no role hierarchy and no kicking, and
it restores per-student channel-level control with the server still open. Recorded as the
first post-launch extension.

### The poller: one mechanism, two kinds of work

Described once here, because every timed behavior in the design depends on it and the
previous draft described it as two different things without saying which owned the clock.

**A single worker loop, every ~30 seconds, claiming rows with
`SELECT ... FOR UPDATE SKIP LOCKED`.** Each pass does two things in this order:

**1. Due work — dated rows, and these own the clock.** Every timed transition in the
system is a row in `due_work` with a `due_at`, enqueued when the thing it will act on is
created. There are exactly five kinds:

| Row | Enqueued when | Does |
|---|---|---|
| `hold_expiry` | the hold and Checkout session are created | booking `pending_payment` → `expired_hold` |
| `window_open` | the entitlement is created, by the webhook handler | booking `paid` → `active`, entitlement `pending` → `open`, create the one invite |
| `window_close` | same transaction as `window_open` | applies the window-end rule, deletes the code, queues `member_cleanup` |
| `upload_grant_close` | same transaction | closes the `upload_grant` |
| `ingest_matches` | by cron, not by a booking | runs the Go binary's work (see *Minimum Go deliverable*) |

A cancelled booking's `window_open` and `window_close` rows are **deleted in the cancel
transaction**, which is why a `voided` entitlement is never touched again.

**2. Convergence — invite state only.** After due work, the pass compares what
`access_invites` says should be live against `GET /channels/{channel_id}/invites`:

- An entitlement in state `open` with no `access_invites` row at all → create the one
  code. This is how a `window_open` row that failed mid-flight recovers.
- A live code whose entitlement is terminal → delete it, mark the row `deleted`.
- An `access_invites` row in state `issued` that Discord no longer lists → mark it
  `gone` and **do nothing else**. Used, deleted or expired, all the same, no replacement.
- A code on the channel with no `access_invites` row → log it once as unmanaged and
  **leave it alone**.

`access_invites` states are therefore `issued` → `deleted` | `gone`, one row per
entitlement, written only by the poller.

**Bounded authority, trivially so.** The poller touches only invite codes recorded in its
own table. It changes no roles, no member attributes, no channel settings, and removes no
members — it cannot, having neither the permission nor the intent. The
unbounded-destructive-diff hazard the first review cycle caught in the role design cannot
arise.

**Where it stops and a human starts.** The `window_close` row writes the
`member_cleanup` entry in the same transaction as the terminal entitlement state and does
nothing further. Alex removes the student in Discord and ticks the row. Desired state is
recorded and dated; the action belongs to a person; the system does not pretend to know
the difference.

### Cancellation, disputes, and the one manual refund

**The policy, decided 2026-11-13: no refunds.** A booking is a reserved hour. A student
who cancels frees the slot and does not get their money back, at any notice. There is
**one exception and it is not a policy exception but an admission of fault**: when the
platform fails to deliver access at all, Alex refunds by hand in the Stripe dashboard.

**No code in this system issues a refund.** There is no refund API call, no refund queue,
no retry with backoff, no `refund_failed` state, and no operator refund control. That is
roughly 4 hours of machinery deleted, and with it the six blocking defects the previous
draft's refund branching produced.

| Event | Slot | Money | Access |
|---|---|---|---|
| **Student cancels**, any notice, before window start | Released | **None.** No refund, stated at checkout | Entitlement `voided`; no code is ever minted; no `member_cleanup` row |
| **Alex cancels**, before window start (`/ops`) | Released | **Alex refunds by hand.** Our fault, so the exception applies | Entitlement `voided`; student emailed |
| **Window elapses, a code was issued** (attended or not — the system cannot tell and does not try) | Consumed | None | Booking `completed`, entitlement `closed`, `member_cleanup` queued |
| **Window elapses, no code was ever issued** (platform failure) | Consumed | **Alex refunds by hand.** Red in `/ops` until the refund webhook arrives | Booking `completed_unfulfilled`, entitlement `expired_unfulfilled`, `member_cleanup` queued |
| **Slot lost after payment** (`payment_orphaned`) | n/a | **Alex refunds by hand.** Red in `/ops` | No entitlement was created |
| **Refund webhook arrives**, from any source | Untouched | Recorded | None. Appended to `money_events`; no state changes |
| **Dispute or chargeback**, at any time | Untouched | Recorded | None. Appended to `money_events`; red in `/ops`; Alex responds in the Stripe dashboard |

**One rule for inbound money, which replaces two disambiguation rules.** The previous
design needed to tell an operator cancellation from an operator refund from a dispute,
by inspecting a bare Stripe webhook that carries no intent. With no app-issued refunds
there is nothing to disambiguate: **every refund or dispute webhook is, by definition,
something that happened outside this application.** The handler verifies the signature,
dedupes on `event.id`, appends to `money_events`, and stops. It never touches a booking
state, an entitlement, a slot or an invite.

That is what makes a three-week-old chargeback safe. It lands as a `money_events` row on
a `completed` booking and changes nothing else — no reanimated entitlement, no second
cleanup task, no request to delete an invite that expired in November.

**What the student is told, and where.** The policy is displayed at three points, because
an undisclosed no-refund policy is both unfair and the easiest kind of dispute to lose:

1. **On the booking page before payment**, beside the price: *"Sessions are
   non-refundable. If you cannot attend, you can cancel to free the slot, but the fee is
   not returned. If I fail to deliver your session, I refund you in full."*
2. **In Stripe Checkout itself**, via `custom_text.terms_of_service_acceptance` with
   `consent_collection` requiring a tick, so acceptance is recorded on the Stripe session
   and is retrievable as dispute evidence.
3. **In the confirmation email**, in the same words.

**Why the platform-failure exception is kept even though it costs a manual step.**
Scenario: the student pays $40, the worker is down at 2:00, no invite is ever created,
and the hour passes with her on the booking page and Alex alone in the voice channel.
Keeping that money is wrong on its own terms, and it is also the most losable dispute
this business could have — "services not received", with our own `access_events` log as
the complainant's evidence. Honouring it costs **zero lines of refund code**: the
window-end row writes `completed_unfulfilled`, `/ops` shows the row red, Alex refunds in
the Stripe dashboard, and the resulting webhook lands in `money_events` through the same
source-agnostic path as everything else. The red row clears when that row appears.

**Coach no-show is the same case.** If Alex does not attend, access was still granted, so
the automatic path writes `completed` and nothing flags it. That is a real gap in an
automated system and it is closed operationally rather than in code: Alex marks the
booking in `/ops`, which writes a `money_events` note and raises it red, then refunds by
hand. Stated here so it is a decision rather than an omission.

### Operations and notifications

- **`/ops` page, really authenticated.** Discord OAuth plus an owner-ID allowlist
  (`OPS_OWNER_DISCORD_IDS`); the previously planned env var remains **only** as an
  additional kill switch, because an env var controls whether a route exists, not who
  may reach it. The page shows booking state, window, last reconcile timestamp, the
  `money_events` attached to each booking, **a red list that is now the system's whole
  escalation surface** — failed reconciler actions with retry, every
  `completed_unfulfilled` and `payment_orphaned` booking awaiting a manual refund, and
  every open dispute — and **the outstanding `member_cleanup` queue**. Two operator
  controls:

  - **Cancel booking** — releases the slot and voids the entitlement. Available only
    before window start. **It moves no money**, because no code in this system does. If
    the cancellation is Alex's fault the booking is flagged for the manual refund and
    turns red; if the student cancelled, nothing is owed and nothing turns red.
  - **Confirm removal** — marks a `member_cleanup` row `done`. It performs no Discord
    call, which is the whole point: the platform records the obligation and its
    discharge and never acts on a member. It verifies nothing, and that is explicit —
    the bot cannot see who is in the server, so `done` is Alex's word for it. The column
    is labelled *"removal confirmed by operator"* rather than *"removed"*, so the
    dashboard never overstates what the system knows.

  **There is no refund control, and that is the design.** A red row names what is owed
  and why; Alex refunds in the Stripe dashboard; the resulting webhook appends to
  `money_events` and clears the red. The application never calls Stripe's refund API, so
  there is no refund to fail, retry, exhaust or reconcile. No review-marking controls
  exist either, because fulfillment is window closure for every SKU. The page displays a
  student's Discord username, their Riot ID and the Stripe payment-intent ID — never
  card data, which never reaches the app, and never an email address.

- **A red row is an obligation with a name.** Each carries the reason
  (`completed_unfulfilled`, `payment_orphaned`, `dispute_opened`, or a failed reconciler
  action), the amount, the student, and how long it has been red. This list is the only
  thing standing between a platform failure and a student who paid for nothing, so it is
  the one screen in the system worth checking daily.

- **Students cancel from the booking page**, authenticated by their Discord login and
  linked from the confirmation email. The control states plainly that cancelling frees
  the slot and does not return the fee. It disappears at window start, when there is
  nothing useful left to cancel.

### Minimum Go deliverable (mandatory, no cut rank)

A standalone Go binary, not a service and with no HTTP server: take a Riot ID, resolve it
to a PUUID, fetch the last 20 match IDs and summaries, upsert them into Postgres.
Rate-limited, retrying, idempotent on match ID.

**Where its input comes from.** The `riot_id` captured on the booking form (see *Identity
and payment*). The binary reads distinct Riot IDs from `bookings` rather than taking an
argument, so it has a real source inside the product rather than a value someone types.
*(Resolves the previous draft's gap: Premise 2 committed to a Riot-ID profile field that
existed in no schema, UI or phase, leaving the one mandatory Go component with no input.)*

**How it runs, which the previous draft never said:**

- **Invocation:** the same `due_work` table as everything else. An `ingest_matches` row is
  enqueued by a daily cron and claimed by the worker, which shells out to the binary. One
  mechanism for all timed work, so there is nothing new to operate.
- **Database:** the managed PaaS Postgres, the same instance the web app uses, reached
  through the same `DATABASE_URL`. It writes one table, `riot_matches`, which nothing on
  the money path reads.
- **Container:** built into the same Docker image as the app, as a second binary. No
  second deployment target, no ECS task, no separate CI job.
- **The key problem, stated honestly.** A Riot **development** key expires every 24 hours
  and must be regenerated by hand on Riot's site. There is no way to automate that, so on
  a dev key this component produces rows only within 24 hours of Alex pasting a fresh key
  into the PaaS environment. More than 24 hours later it logs an auth failure and exits
  cleanly, affecting nothing else. **That is the normal state of the deployment** unless
  the production key lands (Open Question 5), and an evaluator following the live link
  would see a populated `riot_matches` table only if Alex refreshed the key that day. The
  README says this in plain words and shows the committed rows, rather than implying a
  pipeline that runs itself.
- **On a production key** the same binary runs daily with no manual step. The only change
  is the key's lifetime, which is why the design does not branch on it.

It ships unconditionally. Premise 4 calls a Go component mandatory, and it is scheduled
late (Phase 9) on purpose: it is standalone, cannot break the money path, and depends on
nothing but the schema, so it can move earlier freely.

### Why this ordering

The money path stays in TypeScript because Alex is new to Go and that path is where
silent idempotency and ordering bugs live. Go lands where failure is harmless and
retryable. The access model is convergent state rather than fired events, which is
what makes the reconciliation loop — and therefore the whole Beagle analogy —
possible. That survived the 2026-11-13 simplification intact: invite codes are state
to be diffed exactly as roles were, and the loop lost its destructive reach over
members without losing its shape. What it gained is a boundary it can state in one
sentence — it touches only codes it issued — and a last mile it hands to a person
with a dated record, which is a more defensible system than one that ejects people
using a Discord behavior nobody has tested.

## Mandatory tests (the floor; CI runs all ten on push)

**Test strategy, because five of these touch third parties.** Discord is a **fake
client** implementing the three calls used (create invite, list channel invites,
delete invite) over an in-memory channel model — down from four, and none of them
mutate a member, which is why the fake is now small enough to trust; Stripe webhooks
are **replayed fixtures** posted to the real handler with real signature verification
against a test secret. Tests 3 and 8 run against a **real PostgreSQL** service container,
because they assert database behavior and a double would prove nothing. No test needs
live Discord or Stripe credentials, so the whole suite runs on push. A manual
smoke script exercises the real APIs once per deploy, separately from CI.
**Time is a double too:** due-at timestamps and window boundaries are seeded relative
to the test clock and the poller is invoked directly for a single pass, so no test
waits out a 31-minute hold expiry or a 60-second poll interval.

1. **Hold expiry transitions and releases.** After the hold's expiry instant the
   poller writes `expired_hold`, and a second booking for the same range then
   succeeds. Asserted as a state transition and an ordering — not as Stripe's live
   refusal, which cannot occur inside a push build given the 30-minute floor.
2. A replayed Stripe webhook creates exactly one entitlement.
3. Two simultaneous bookings for the same time: one succeeds, one is rejected by the
   exclusion constraint. A 2-hour Both booking is rejected when it would span an
   existing 1-hour booking, and accepted into a clear 2-hour-plus-gap opening.
4. **Boundary behavior as inequalities, not instants, plus the stale-clock guard:** no
   invite code exists before window start; a code is observed within 60 s after window
   start; the code is gone within 60 s after window end. Then the negative case that
   carries the real risk — **a pass run after `ends_at` against an entitlement still
   stored `open` creates no invite** and drives the entitlement terminal instead. The
   first and last assertions are the core product guarantee and neither may go soft.
5. **Money moving backwards changes no state.** A replayed refund webhook and a replayed
   dispute webhook, each against a `completed` booking, append one `money_events` row
   apiece and leave the booking `completed`, the entitlement `closed`, the slot consumed
   and `member_cleanup` untouched. Re-delivery of the same `event.id` adds nothing. This
   is the assertion that keeps a three-week-old chargeback from reanimating a finished
   session.
6. **The poller converges, and respects its boundary.** Four assertions, two of which
   are about *not* acting: an entitlement reaching `open` with no row gets exactly one
   code; **a code deleted out from under an open entitlement is marked `gone` and no
   replacement is created**, which is the no-reissue decision and the thing that keeps
   `max_uses: 1` meaningful; an entitlement reaching `closed` has its code deleted and a
   `member_cleanup` row written; and a code on the channel with no `access_invites` row
   is logged once as unmanaged and **left alone**. No member, role or channel setting is
   touched in any pass, asserted positively rather than by omission.
7. **Crash between Discord and Postgres.** The worker killed after creating an invite but
   before committing the code, then restarted: the next pass finds a channel invite with
   no matching `access_invites` row, logs it unmanaged and **leaves it alone**, and
   because the entitlement has no row it issues its one code. The orphan is never deleted
   by the app and needs no deletion — its own `max_age` expires it no later than
   `ends_at`. **That argument is sound only because every issued code carries a strictly
   positive `max_age` ending at or before window close**, with no round-up anywhere, so
   this test and test 4's guard assertion stand or fall together. Assert also that the
   orphan is the one case where a booking can end up with two live codes, and that both
   die by `ends_at`.
8. **The 15-minute gap, and a blackout, are both rejected at the database.** A booking
   starting less than
   15 minutes after an existing booking's end is refused by the exclusion
   constraint — asserted by inserting directly, bypassing the booking service, so the
   trigger-maintained `reserved` column is exercised too. A booking overlapping a
   `blackouts` row is refused the same way and by the same constraint, asserted the same
   way, so Alex being ill cannot be sold.
9. **Fulfillment does not depend on attendance.** Two entitlements, identical except
   that one has `consumed_at` set and one does not, both resolve at window end to
   booking `completed` / entitlement `closed` with no refund enqueued. Then the
   platform-failure case: an entitlement whose every invite-creation attempt failed
   resolves to `completed_unfulfilled` / `expired_unfulfilled` and is **flagged red for a
   manual refund with no Stripe call made by the app**. Then the late-pass case: the same
   window-end row run an hour after `ends_at` against an entitlement that *did* issue a
   code resolves `completed` / `closed` and flags nothing, proving the rule is keyed on
   the code record rather than the clock.
10. **An unused code changes nothing.** A code is issued, never clicked, and the window
   closes: the booking reaches `completed`, the entitlement `closed`, the code is
   deleted, a `member_cleanup` row is `queued`, and **no refund row is written**. This
   is the assertion that keeps the returning-student case safe without the system
   having to recognize it — their session looks exactly like this one and settles the
   same way.
